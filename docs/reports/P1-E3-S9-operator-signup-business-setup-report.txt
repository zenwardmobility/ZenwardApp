2. SIGNUP ARCHITECTURE
--------------------------------------------------------------------
`/sign-up` collects exactly 4 fields (full name, email, password,
business name — work item §2's own explicit minimum). The Server
Action (`src/app/sign-up/actions.ts`) calls real Supabase Auth
`signUp()` — never a service-role shortcut, never reachable from the
browser — then, ONLY if a real session came back (see §4 below), calls
`signup_create_organization`, a new SECURITY DEFINER RPC that
atomically creates the caller's UserProfile, a new Organization, and
their own `organization_admin` Membership in ONE transaction. `state`/
`role` are Postgres literals in the function body — never parameters —
mirroring `create_trip`'s own established, already-reviewed pattern.
Full design: `docs/product/operator-onboarding-model.md`,
`docs/product/onboarding-data-map.md`. Decision record: ZD-193.

Deliberately, `organizations`/`memberships` still carry NO raw INSERT
grant to `authenticated` — the RPC remains the sole controlled path,
consistent with the pre-existing "organization creation is a platform-
level action" framing (only WHO may trigger it changed, not the
mechanism).

3. ORGANIZATION CREATION — ATOMICITY AND FAILURE-MODE HONESTY
--------------------------------------------------------------------
Verified live and via SQL (SIGNUP-1 through SIGNUP-6 in

6. OWNER-OPERATOR MODE
--------------------------------------------------------------------
Full contract: `docs/product/owner-operator-mode.md`. Supports one
person genuinely holding Owner + Dispatcher + Driver, WITHOUT
collapsing roles insecurely: `link_self_as_driver` creates/reuses a
Driver row linked to the caller's own `auth.uid()` in their own
organization, and NEVER touches `Membership.role` — an org_admin who
self-links stays exactly the org_admin they were.

**The real, previously-undiscovered gap found and fixed this phase**
(the most significant single finding): `current_driver_id()` — the
function every Driver-scoped RLS policy and RPC ultimately calls — had
required `Membership.role = 'driver'` specifically since P1-E2-S3
(ZD-100's own fix for a genuine vulnerability: an inactive Membership
retaining Driver access through a stale `drivers.status='active'`
row). That made Owner-Operator Mode structurally impossible: an
org_admin's own Membership.role can never equal 'driver'. Found via
direct live testing (not assumed from reading the code alone) when
`/driver` redirected a freshly self-linked owner straight back to
`/operations`. Root-caused to `20260831110300_current_driver_id_
membership_check.sql`'s own role restriction, fixed
(`20260903100700_current_driver_id_owner_operator_mode.sql`) by
relaxing the check to `Membership.status = 'active'` (any role) —
preserving ZD-100's actual security property exactly (still requires
an ACTIVE Membership; still denies on inactive, any role) while
correctly allowing the one new case this phase reviewedly introduces.
See ZD-194. Re-verified: the ORIGINAL ZD-100 regression test
(`driver_read_authorization_tests.sql` DETAIL-6/DETAIL-7) still passes
unchanged, plus a new dedicated test (OWNERDRIVER-5).

The `/driver/*` route guard (`requireDriverAccess`) was relaxed to
also allow `organization_admin`/`dispatcher` through to the SAME
`driver_get_profile` check every Driver already passes through — a
navigation change only; the actual data-access boundary was, and
remains, `current_driver_id()` resolving from the real `drivers`
table, never Membership.role. The sidebar's conditional "Drive" item
and the Driver header's "Back to Operations" affordance are both gated
on this same real, live check.

10. DRIVER INVITE/LINKAGE ARCHITECTURE — the highest-risk part
--------------------------------------------------------------------
Full contract: `docs/product/driver-invite-linkage-model.md`. Closes
GAP-15. Design: a token-gated `driver_invites` record — the
organization admin NEVER creates the invitee's account or handles
their password. The invitee signs up (or signs in) through ordinary
Supabase Auth with the matching email, then redeems the invite
themselves.

Four new SECURITY DEFINER functions, no raw INSERT/UPDATE/DELETE grant
on `driver_invites` at all:
  create_driver_invite    — Organization Admin only, own org only,
                             refreshes rather than duplicates a
                             pending invite for the same email
  revoke_driver_invite    — Organization Admin only, pending only
  get_driver_invite_preview — public/anon-callable, token-gated,
                             returns only org name/invited name/
                             email/status — never organization_id
  redeem_driver_invite    — any authenticated user whose OWN account
                             email matches the invite; takes NO
                             organization_id parameter at all (always
                             resolved from the invite row) — making
                             cross-org redemption not merely denied
                             but structurally unexpressible

Every explicit requirement from work item §10 verified, live and via
SQL (9 dedicated tests: INVITE-1 through INVITE-6, REDEEM-1 through
REDEEM-5):
  - Organization Admin only                     INVITE-5 (Dispatcher denied)
  - Tenant-scoped                                INVITE-4 (foreign-org admin denied)
  - Invite cannot create foreign-org membership  Structural — no org_id parameter exists
  - No orphan Driver/Auth on partial failure     Structural — auth user created by a
                                                  separate, already-atomic signUp() call
  - Invited Driver receives Driver role only     REDEEM-2
  - Driver record distinct from Membership/AuthUser  Unchanged, verified throughout
  - Revoked/inactive Membership loses access immediately  ROLE-REVOKE-1
  - Duplicate invite/link handled safely         INVITE-2/3 (reused, not duplicated),
                                                  REDEEM-4 (idempotent repeat redemption)
  - Audit important actions                      driver_invite_created/_revoked/_redeemed,
                                                  all real audit_events rows

**A related real gap found and fixed while building this**: before
this phase, `drivers.user_id` carried a broad, unconditional client
UPDATE grant (`drivers_update_org_admin`, with no constraint on WHAT
VALUE `user_id` could be set to) — an organization_admin could set any
Driver row's `user_id` to any `auth.users.id`, including an unrelated
person's account, silently granting them Driver access without
consent. Never exercised by any shipped feature before now, but
genuinely live-exploitable. Fixed
(`20260903100300_retire_direct_driver_user_id_update.sql`): the column
is no longer in the client grant at all — `link_self_as_driver` and
`redeem_driver_invite` (both structurally self-only) are the sole
paths that ever set it now. See ZD-195.

Full live browser verification: create an invite as Org Admin → the
invitee visits `/join/[token]` (unauthenticated, sees the real
organization/invited name via the token-gated preview) → signs up with
the locked, matching email → lands on `/driver` → real `driver`
Membership + linked Driver row confirmed in the database → invite
marked accepted.
