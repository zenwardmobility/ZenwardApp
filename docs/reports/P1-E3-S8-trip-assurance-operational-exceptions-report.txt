2. PRODUCT FRAMING
--------------------------------------------------------------------
Trip Assurance is the first product-differentiation layer built this
project — the operational substrate a future "ZENWARD TRIP ASSURANCE"
commercial concept could rest on, but no such surface (scoring,
marketing claims, facility-facing SLA dashboard) is built or implied
this phase. It answers one question for a Dispatcher: "which Trips need
my attention right now, and why?" — nothing more. No AI language, no
predictive/forecasted claims, no Facility Portal, no billing, no route
optimization were introduced (work item's own explicit non-goals).

--------------------------------------------------------------------
3. ARCHITECTURE DECISION — DERIVED, NOT PERSISTED
--------------------------------------------------------------------
Trip Assurance is computed at read time, never written to `trips.state`
or any new column (ZD-169). One pure function,
`evaluateTripAssurance(facts: TripAssuranceFacts, now: Date):
TripAssuranceCondition` in `src/lib/operations/trip-assurance.ts`, takes
a narrow, explicit fact object (Trip lifecycle state, whether an active
assignment exists, the assignment-scoped latest location if any,
open-exception count) and one centralized `now` — never `new Date()`
scattered through components, never a raw DB row passed in directly.
This keeps the vocabulary trivially re-evaluable and structurally
incapable of drifting out of sync with the facts it explains.

--------------------------------------------------------------------
4. ASSURANCE VOCABULARY (ZD-170)
--------------------------------------------------------------------
Six codes, evaluated in one fixed, deterministic priority order (a real
ranked `if` chain, never row/array order):
  1. TERMINAL              — Trip already in a terminal state
                              (completed/cancelled/no_show) — excluded
                              from active attention regardless of any
                              other condition.
  2. OPEN_EXCEPTION         — >=1 real, persisted `open` trip_exceptions
                              row exists for this Trip.
  3. NEEDS_ASSIGNMENT       — `state == 'scheduled'` and no active
                              TripAssignment (unchanged derivation from
                              prior phases).
  4. LOCATION_UNAVAILABLE / — only evaluated for Trips in one of the 5
     LOCATION_STALE           `ELIGIBLE_LOCATION_TRACKING_STATES`
                               (reused from S7A) AND with an active
                               assignment; reuses `classifyLocationFreshness`
                               and its established thresholds verbatim
                               (no threshold duplication).
  5. ON_TRACK               — none of the above apply. Copy is
                              deliberately conservative ("No current
                              issues"), never overclaiming reliability.
No numeric score exists anywhere (no "Trip Assurance Score 84/100," no
"Reliability 92%") — every condition carries a code, a human label, a
human explanation, and its source facts; nothing opaque.

6. EXCEPTION AUTHORIZATION — WHY TWO RPCs, NOT DIRECT WRITES (ZD-172)
--------------------------------------------------------------------
The pre-existing `trip_exceptions` RLS policies (present since
P1-E2-S1, deferred at P1-E3-S6) were inspected before building against
them:
  - `trip_exceptions_insert_assigned_driver` — already narrow and safe
    (org match, `is_driver_assigned_to_trip`, `created_by`/`status`
    forced) — reusable as-is.
  - `trip_exceptions_insert_operations` — org-scoped but did NOT force
    `created_by`/`status`, an impersonation/fabricated-history risk.
  - `trip_exceptions_update_operations` — org-scoped but had NO column
    restriction at all — a raw UPDATE could rewrite any field on a
    resolved historical row or silently reopen it.
Conclusion: rather than split the write path across two mechanisms for
one logical action, both actor populations (Operations AND the Trip's
own ever-assigned Driver) now go through the same controlled RPC pair.
The old direct policies were deliberately NOT revoked (narrowing them
correctly would require rebuilding the same restriction the RPCs
already provide) — documented, not silently left as a forgotten gap
(see rls-model.md, mutation-authorization.md).

--------------------------------------------------------------------
7. report_trip_exception (CREATE)
--------------------------------------------------------------------
`report_trip_exception(p_trip_id uuid, p_exception_type text default
null, p_description text default null) returns trip_exception_result`.
SECURITY DEFINER. Callable by Operations (organization_admin/dispatcher,
any Trip in their org) OR the Trip's own ever-assigned Driver. Forces
`created_by = auth.uid()` and `status = 'open'` structurally (not by
convention) for both actor types. Validates description non-blank and
<=2000 chars if provided. Exception type is a restrained 7-value
application-layer list (driver_issue, vehicle_issue,
passenger_not_ready, pickup_issue, facility_delay, route_issue, other)
— not database-enforced (the column's own schema comment says taxonomy
is not yet finalized), but the UI only ever offers these 7. Writes one
`trip_events` row (`exception_flagged`) — a CHECK-constraint value
allow-listed since the very first schema migration but unused until
this phase. No AuditEvent (see §9).

--------------------------------------------------------------------
8. resolve_trip_exception (RESOLVE)
--------------------------------------------------------------------
`resolve_trip_exception(p_exception_id uuid, p_resolution_note text
default null) returns trip_exception_result`. SECURITY DEFINER.
Operations-only (organization_admin/dispatcher) — Driver never resolves,
matching the schema's own original comment. ZW002 (not_found, no
existence oracle) if the exception does not exist or the caller has no
org role over it. Idempotent no-op (ZD-173): a second resolve of an
already-resolved exception returns the real, already-persisted
resolution untouched (`changed=false`) rather than raising a conflict —
deliberately looser than `reassign_trip`'s fail-closed staleness
contract (P1-E3-S5B), because two resolutions of the same exception can
never disagree about the operationally relevant fact ("is this
handled?"), unlike a reassignment's driver/vehicle choice. Never
deletes — history is preserved. Writes one `trip_events` row
(`exception_resolved`) only on a real resolve.

--------------------------------------------------------------------
9. NO AUDITEVENT FOR EXCEPTIONS
--------------------------------------------------------------------
Neither RPC writes `audit_events`. Reporting/resolving an operational
exception does not "materially change responsibility or reach a
terminal disposition" of the Trip itself (ZD-087's own literal test) —
it is an operational flag, not an administrative mutation of who owns
or how a Trip concludes. Matches the already-established precedent that
`trip_notes` (Add Note) also writes no AuditEvent.

10. TODAY'S OPERATIONS — REAL ATTENTION QUEUE
--------------------------------------------------------------------
`getTodaysOperationsData` (todays-operations.ts) now runs a second query
phase, scoped to exactly the candidate Trip id set already resolved by
the first phase (never a broader per-org scan — the same two-phase
discipline established in dispatch-board.ts, S7A): open `trip_exceptions`
(id/trip_id/exception_type/created_at only — list-surface read
minimization) and `getLatestLocationsByTrip` for the eligible-tracking
subset. `evaluateTripAssurance` is run once per candidate Trip against
one shared `now`. `attentionItems` are sorted by a real rank map
(`PRIORITY_RANK`: OPEN_EXCEPTION:0, NEEDS_ASSIGNMENT:1,
LOCATION_STALE:2, LOCATION_UNAVAILABLE:3) then by `scheduledPickupAt` —
never database/array insertion order. Each row shows Passenger/Trip,
the single primary reason, current state/assignment context, and a real
destination action ("Assign" -> Dispatch for NEEDS_ASSIGNMENT, "Open
Trip" -> Trip Detail otherwise) — never a generic "Review" link. One
Trip, one row (deduplication verified — see §16).
