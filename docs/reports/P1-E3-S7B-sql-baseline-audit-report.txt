4. ROOT CAUSE
--------------------------------------------------------------------
**A reporting error, not a security regression.** The file has always
contained exactly 32 distinct test scenarios and has always produced
exactly 32 PASS/FAIL result lines when run — confirmed independently at
FOUR separate points in this project's history, all agreeing:

  P1-E2-S2  completion report: "rls_adversarial_tests.sql   32/32  PASS"
  P1-E2-S2A completion report: "rls_adversarial_tests.sql   32/32  PASS"
  P1-E2-S3  completion report: "rls_adversarial_tests.sql   32/32  PASS"
                                (even after tests F/I were edited that
                                same phase — still 32, a modification,
                                not an addition/removal of a test)
  P1-E3-S2  completion report: "...and the 32 rls_adversarial_tests.sql
                                assertions..."
  P1-E3-S4  completion report: "rls_adversarial_tests.sql   33 assertions"
                                ← THE ERROR FIRST APPEARS HERE
  P1-E3-S5, S5A, S5B, S6:      "rls_adversarial_tests.sql   33 assertions"
                                ← mechanically copied forward, unverified,
                                for 4 more consecutive phases
  P1-E3-S7  completion report: "rls_adversarial_tests.sql   32 assertions"
                                ← correct count restored, by actually
                                re-tallying from a fresh run's raw output
                                rather than copying the prior report's
                                own table forward

The "33" figure was introduced as a manual miscount in P1-E3-S4's own SQL
regression section — most plausibly, the trailing summary line the test
file itself prints (`=== RLS adversarial test suite complete — review
PASS/FAIL lines above ===`, a `NOTICE:` line just like every real test
result) was counted alongside the 32 genuine `TEST <label>: PASS/FAIL`
lines during a manual or loosely-automated tally, producing 33. That
incorrect figure was then reused as the "known" baseline by P1-E3-S5,
S5A, S5B, and S6's own SQL regression sections without independently
re-deriving it from a fresh run each time — an unverified copy-forward
chain, not a re-audit. No test was ever added, removed, renamed, or
disabled at any point; no assertion ever failed to execute; the counting
convention (grep `NOTICE:.*: PASS`/`: FAIL`) is unchanged and was applied
identically in this audit.

**Conclusion: 220/32 (P1-E3-S7's own figures) are correct. 221/33 (P1-E3-
S4 through P1-E3-S6's figures) were incorrect** — an over-count of
exactly 1, isolated entirely to this one file's own reported total, that
persisted uncaught for four consecutive phases until this audit.
