2. ORIGINAL DIRECT TRIP INSERT EXPOSURE
--------------------------------------------------------------------------------
Confirmed by direct migration inspection (not inferred): `supabase/
migrations/20260830131700_rls_policies.sql` line ~267 granted
`select, insert, update on public.trips to authenticated` — a single
combined grant. UPDATE was subsequently revoked and re-granted only for
8 specific planning columns (same migration, later section). INSERT
received no equivalent narrowing anywhere, ever — gated only by the
`trips_insert_org_operations` RLS policy, which checks org role but not
which columns a client sets. A raw INSERT under that policy could
therefore set `state` to any of the 9 canonical values, or populate
`completed_at`/`cancelled_at`/`no_show_at` directly, at creation time —
a real, currently-exploitable bypass of the lifecycle model, not merely
a missing feature. This is exactly what P1-E3-S0 (GAP-1) found and this
phase exists to close.

5. AUTHORIZATION CHAIN
--------------------------------------------------------------------------------
auth.uid() present -> has_org_role(p_organization_id, [organization_admin,
dispatcher]) live-checked (ZW002 uniformly for wrong role, inactive
Membership, or foreign organization — no distinction, matching the
established anti-oracle convention) -> Passenger exists, same org,
active (ZW006) -> Facility references (if supplied) exist, same org,
active (ZW006) -> Request (if supplied) exists, same org, state in
(pending, accepted) (ZW006) -> INSERT -> conditional Request state
transition -> TripEvent -> AuditEvent -> typed result. organization_id
is a REQUESTED context throughout, never trusted authority on its own —
identical treatment to every check that follows it.

--------------------------------------------------------------------------------
6. INITIAL-STATE ENFORCEMENT
--------------------------------------------------------------------------------
'scheduled' is a fixed literal inside the function body's INSERT
statement — there is no code path, correct or malicious input, by which
a caller can influence it. Verified structurally (create_trip_tests.sql
TEST STATE-1: the function's own pg_proc.proargnames contains no
state-named parameter) and behaviorally (TEST STATE-2: every Trip this
suite created is state='scheduled', with no exception).

7. PASSENGER VALIDATION
--------------------------------------------------------------------------------
Required (ZW006 if null). Must exist, same organization_id as the
validated context, status='active'. Foreign-org and nonexistent
passenger_id produce the identical ZW006 — no existence oracle. Verified:
create_trip_tests.sql TEST VAL-1.

--------------------------------------------------------------------------------
8. FACILITY VALIDATION
--------------------------------------------------------------------------------
Optional on both pickup and destination (the canonical model permits
address snapshots with no Facility reference at all — trips.
pickup_facility_id/destination_facility_id are both nullable). Where
supplied, validated for tenant consistency and active status, same ZW006
categorization as Passenger. Verified: TEST VAL-2.

--------------------------------------------------------------------------------
9. REQUEST VALIDATION
--------------------------------------------------------------------------------
Optional (request_id is nullable on trips, exactly as the canonical model
specifies). When supplied: must exist, same organization, and be in state
pending or accepted (declined/cancelled rejected as no-longer-usable,
ZW006). Locked FOR UPDATE for the duration of the transaction. 1:N
Request->Trip is explicitly preserved — an already-accepted request (a
return-leg scenario) is a legitimate second create_trip call, not an
error. Verified: TEST VAL-3 (pending, transitions to accepted), TEST
VAL-3B (TripEvent + state transition confirmed), TEST VAL-4 (already-
accepted, second Trip allowed), TEST VAL-5 (declined, rejected), TEST
VAL-6 (foreign-org request, rejected), TEST VAL-7 (no request at all,
allowed, schema permits this per domain-model.md).

12. TRIPEVENT BEHAVIOR
--------------------------------------------------------------------------------
Exactly one event per successful call, reusing the EXISTING allow-listed
vocabulary (no schema/CHECK-constraint change was needed):
'request_converted_to_trip' when request_id was supplied,

--------------------------------------------------------------------------------
13. AUDITEVENT BEHAVIOR
--------------------------------------------------------------------------------
One AuditEvent per successful call: entity_type='trip', action=
'trip_created', actor_user_id=auth.uid(), before_data=null (nothing
existed before), after_data={state, passenger_id, request_id} only — no
Passenger name/phone, no free-text pickup/destination, matching the
"metadata must be minimal" instruction and every other AuditEvent's
existing minimalism in this codebase.

14. ATOMICITY
--------------------------------------------------------------------------------
Trip INSERT + conditional Request UPDATE + TripEvent INSERT + AuditEvent
INSERT all occur in one PL/pgSQL function with no internal exception
handler — a failure anywhere rolls back everything. Proven, not asserted:
a temporary trigger (installed and removed within the same test run, never
a permanent object) forced the AuditEvent insert to fail for a dedicated
atomicity-test Passenger; the result confirmed zero Trip rows, zero
TripEvent rows, and the TransportationRequest still 'pending' (not
advanced) after the forced failure. create_trip_atomicity_tests.sql,
2/2 PASS.

--------------------------------------------------------------------------------
15. IDEMPOTENCY DECISION
--------------------------------------------------------------------------------
Deliberately NON-idempotent (ZD-102). No duplicate-submission heuristic
based on Passenger/time/address was implemented — two legitimate Trips
can share all three, and a false-positive "duplicate" rejection would be
a real product harm. `created` is always `true` in the response.
Preventing accidental double-submission is explicitly left to future
application code (e.g. disable-on-submit), not solved at the database
layer in this phase, per explicit instruction not to invent weak
detection logic.
