12. ROLE RESOLUTION
--------------------------------------------------------------------------------
Never a single global role — `resolveOrganizationContext()` returns a role
scoped to one specific organization at a time. A user's role in Org A has
zero influence on their authorization in Org B (verified: REVOKE-3a/3b,
FOREIGNORG tests).

--------------------------------------------------------------------------------
13-16. ORGANIZATION-CONTEXT / SINGLE-ORG / MULTI-ORG / ORG-SELECTION
IMPLEMENTATION
--------------------------------------------------------------------------------
`resolveOrganizationContext()` returns `none`/`single`/`selected`/
`select-required`. Single active Membership auto-selects with no extra
screen. Multiple require `/select-organization` — a plain, server-rendered
list (org name + role, via the existing design system, not a new
component) whose selection is re-validated against a fresh
`getActiveMemberships()` call before the `zw_org_context` cookie
(httpOnly, sameSite=lax) is set — a user cannot select an org by supplying
an arbitrary UUID. The cookie is never trusted as authorization by
itself: every subsequent read re-validates it, and a value matching none
of the caller's own active Memberships (forged or stale) is treated
exactly like no cookie at all.

17. NO-MEMBERSHIP BEHAVIOR
--------------------------------------------------------------------------------
`/access-unavailable` — authenticated, zero active Memberships. Calm copy,

18. OPERATIONS AUTHORIZATION
--------------------------------------------------------------------------------
`requireOperationsAccess()`: auth → org context → role in
{organization_admin, dispatcher} for THAT organization. A `driver`
Membership is redirected to `/driver` (not a bare denial) — the "wrong
surface for this role" case is distinguished from "no access at all."

--------------------------------------------------------------------------------
19-20. DRIVER AUTHORIZATION / DRIVER LINKAGE BEHAVIOR
--------------------------------------------------------------------------------
`requireDriverAccess()`: auth → org context → role=driver for that
organization → a genuinely linked, active `drivers` row, confirmed by
calling the SAME `driver_get_profile` RPC the secure Driver read API
already uses (reusing the database's own authoritative
`current_driver_id()` check rather than re-deriving it in TypeScript). A
`driver` Membership with no resolvable Driver row does NOT redirect
(would loop back into this same guard) — it returns a discriminated
`link-missing` result, and the `/driver` layout renders a safe inline
"account not yet set up" state with a sign-out action, no internal ID
exposed. A new seed fixture (`org-a-driver-nolink@example.test`) was added
to exercise this path with real data.

21. INACTIVE MEMBERSHIP REVOCATION
--------------------------------------------------------------------------------
Verified with the SAME authenticated session throughout (no re-sign-in):
an active Membership toggled to `inactive` via direct `psql` mutation
loses `/operations` access on the very next request, redirected to
`/access-unavailable`. Reactivating it restores access immediately, same
session. See §31 for the full same-session test record.

22. ROLE-CHANGE REVOCATION
--------------------------------------------------------------------------------
Same-session: dispatcher → operations works; role changed to `driver` mid-

to the inline link-missing state, since that fixture user has no `drivers`
row); role restored → operations works again immediately. No stale role
cache anywhere.

27. REDIRECT SAFETY
--------------------------------------------------------------------------------
`isSafeRedirectPath()` — allowlist-based (`^\/[A-Za-z0-9\-_/]*(?:\?...)?$`,
rejects `//`, backslashes). Every `next`/`returnTo` value in the
application passes through this single function before reaching
`redirect()`. Verified with real malicious values (`https://evil.example`,
`//evil.example`, `javascript:alert(1)`, `/\evil.example`) submitted both
as a query parameter AND through a real POST to the actual sign-in Server
Action — none were ever carried into a redirect target.

29. SEED/TEST-USER CHANGES
--------------------------------------------------------------------------------
One new fixture added to `supabase/seed.sql`:
`org-a-driver-nolink@example.test` — an active `driver`-role Membership in
Org A with NO corresponding `drivers` row, needed to exercise the
link-missing state with real data (work item §53 item D). Full regression
(204 SQL assertions) re-run after this change from a clean
`supabase db reset` — zero regressions.

**Separately, and more significantly:** `getActiveMemberships()`'s first
implementation had a real bug, found by this phase's own integration
testing (not assumed correct): it queried `memberships` filtered only by
`status='active'`, relying on RLS alone to scope results to "my own rows."
`memberships` carries a second applicable policy,
`memberships_select_org_admin`, which legitimately lets an
`organization_admin` see every membership row in their own organization
(RLS policies OR together, they don't narrow each other) — so the
unfiltered query returned an org_admin's entire team's memberships, not
just their own, causing a single-Membership Org Admin to be incorrectly
resolved as a multi-org user. Fixed by adding an explicit
`.eq("user_id", user.id)` filter. Recorded as ZD-110. This was an
application-layer query-intent bug, not an RLS gap — RLS correctly
protected the table throughout; no cross-tenant data was ever exposed to
the wrong tenant at any point.
