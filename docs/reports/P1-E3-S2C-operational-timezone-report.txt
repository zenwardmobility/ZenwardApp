1. ORIGINAL DEFECT
--------------------------------------------------------------------
Driver Today (`src/app/driver/page.tsx`, `src/lib/driver/
trip-presentation.ts`) computed "today," trip-date grouping, and every
displayed time/date using `Intl.DateTimeFormat` with no explicit
`timeZone` — i.e., whichever timezone the Next.js server process
itself happened to run in. Correct only by coincidence when server
and organization agree; a real operational-correctness defect the
moment they don't (a late-evening organization-local trip can be
grouped onto the wrong calendar day by a server in a different zone).
This was a known, explicitly documented simplification from P1-E3-S2
(ZD-116), not a silently-introduced bug — this phase replaces it with
a correct mechanism.

3. VALIDATION MECHANISM
--------------------------------------------------------------------
`public.is_valid_iana_timezone(text) returns boolean`, `STABLE`
(genuinely queries the `pg_timezone_names` system catalog — not
`IMMUTABLE`), no `SECURITY DEFINER` (needs none — `pg_timezone_names`
is already publicly readable):

    select p_timezone is not null
      and (p_timezone = 'UTC' or p_timezone like '%/%')
      and exists (select 1 from pg_timezone_names where name = p_timezone);

**Why the `/`-or-`UTC` rule, not bare catalog membership:** confirmed
empirically that `pg_timezone_names` itself contains legacy
backward-compatibility entries — `EST`, `EDT`, `PST8PDT`, `Japan`,
`GMT-0`, and 41 others — that a bare `exists (select 1 from
pg_timezone_names where name = p_timezone)` check would incorrectly
accept, despite being exactly the ambiguous/fixed-offset class this
work item names for rejection. Live-tested against the actual
catalog before writing the constraint (not assumed):

    is_valid_iana_timezone('America/New_York') → true
    is_valid_iana_timezone('America/Chicago')   → true
    is_valid_iana_timezone('Africa/Lagos')       → true
    is_valid_iana_timezone('UTC')                → true
    is_valid_iana_timezone('Etc/UTC')            → true
    is_valid_iana_timezone('EST')                → false
    is_valid_iana_timezone('EDT')                → false
    is_valid_iana_timezone('GMT-5')              → false
    is_valid_iana_timezone('Georgia')            → false
    is_valid_iana_timezone('Eastern')            → false
    is_valid_iana_timezone(null / '')            → false

**A genuine privilege subtlety, found by empirical testing, not
assumed:** PostgreSQL re-validates every `CHECK` constraint on a row
for **any** `UPDATE`, regardless of which columns actually changed,
under the privileges of the role performing the `UPDATE` (not the
table owner). This project's established pattern for internal helper
functions (`_is_valid_trip_transition` et al.) revokes `EXECUTE` from
`public` — that pattern's safety depends on the helper being called
only from within a `SECURITY DEFINER` wrapper, which a bare `CHECK`
constraint is not. Applying the same revoke-from-public reflex here
was tried and reproduced live: an Organization Admin's ordinary
`UPDATE organizations SET status = 'active' ...` (never touching
`timezone`) failed with `permission denied for function
is_valid_iana_timezone`. Fixed by granting `EXECUTE` to `authenticated`
specifically (not `anon`/`public`) — recorded as ZD-120, including the
reasoning for future internal-helper functions referenced from a
`CHECK` constraint rather than a `SECURITY DEFINER` wrapper. This
function reveals nothing sensitive if called directly (a boolean over
Postgres's own public tzdata catalog), so the broader grant carries no
real exposure risk, unlike the state-machine-revealing helpers this
pattern was originally written to protect.

No new public RPC was added for a timezone-management feature — the
validator exists solely to back the `CHECK` constraint.
