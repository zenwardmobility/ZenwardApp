2. ARCHITECTURE DECISION
--------------------------------------------------------------------
Driver location is treated as narrow, operational Trip data — collected
only while it serves an active transportation execution (work item §3).
Full rationale in the new docs/product/driver-location-architecture.md.
Core decisions: one append-only history table (ZD-161), a controlled
RPC write path reusing the existing `_lock_driver_active_assignment`
helper (ZD-162), server-authoritative timestamps (ZD-163), a 5-state
eligible tracking window including both "arrived" states (ZD-164),
Realtime deferred in favor of restrained polling (ZD-165), a plain
external-map-link MVP provider decision (ZD-166), zero Driver read
access (ZD-167).

--------------------------------------------------------------------
3. SCHEMA
--------------------------------------------------------------------
`driver_location_updates` (supabase/migrations/
20260902140000_driver_location_tracking.sql): `id`, `organization_id`
(FK), `driver_id`/`trip_id`/`assignment_id` (composite FKs to
`(id, organization_id)` on their respective tables), `latitude` (CHECK
[-90,90]), `longitude` (CHECK [-180,180]), `accuracy_meters` (CHECK >=0
or null), `recorded_at` (default now()), `created_at`. No altitude,
heading, speed, or device identifiers (work item §10 — none has an
actual MVP requirement). `trip_assignments` additionally gained
`unique (id, organization_id)` (additive, purely to support the new
composite FK — no existing behavior changed). Indexes:
`(trip_id, recorded_at desc)`, `(organization_id, recorded_at desc)`,
`(assignment_id)`.

--------------------------------------------------------------------
4. LATEST-VS-HISTORY DECISION
--------------------------------------------------------------------
One table, history only — no separate "latest location" projection
(ZD-161). "Latest" is always derived (`ORDER BY recorded_at DESC` per
Trip, index-backed), directly extending ZD-051's own established
"TripAssignment is the sole source of truth, no redundant current
pointer" reasoning to this new domain.

--------------------------------------------------------------------
5. RETENTION DECISION
--------------------------------------------------------------------
Documented policy: 30 days from `recorded_at`. NOT implemented as an
automated job this phase — no scheduled-job infrastructure (pg_cron,
edge function scheduler) exists anywhere in this project to build one
safely against, and inventing one now would be new, unproven
infrastructure as a side effect of this phase's own primary mandate
(work item §11's own explicit caution). Documented as an explicit,
open future requirement in driver-location-architecture.md §6 — not a
silent gap.

--------------------------------------------------------------------
6. LOCATION-WRITE CONTRACT
--------------------------------------------------------------------
`driver_record_location(p_trip_id uuid, p_latitude double precision,
p_longitude double precision, p_accuracy_meters double precision default
null) returns driver_location_result (location_id, trip_id,
assignment_id, recorded_at)`. SECURITY DEFINER. No authenticated INSERT
grant on the table at all — this RPC is the sole write path (ZD-162).

--------------------------------------------------------------------
7. AUTHORIZATION CHAIN
--------------------------------------------------------------------
1. `auth.uid()` non-null → else ZW001.
2. Trip exists → else ZW002.
3. `is_driver_assigned_to_trip()` (ever assigned) → else ZW002 (no
   existence oracle).
4. `_lock_driver_active_assignment()` — CURRENTLY active assignment →
   else ZW001 (reassignment revocation).
5. `trips.state` in the 5 eligible states → else ZW004 (terminal-state
   and pre-dispatch revocation).
6. Coordinates valid → else ZW006.
`current_driver_id()`'s own existing inactive-Membership/inactive-Driver
correction (ZD-100, P1-E2-S3) is inherited transitively with zero new
code — both surface as ZW002, matching `driver_get_trip_detail`'s own
established convention for the identical situation.

--------------------------------------------------------------------
8. REASSIGNMENT REVOCATION
--------------------------------------------------------------------
Every write is tied to the SPECIFIC `assignment_id` in force at write
time. `_lock_driver_active_assignment()` only ever finds a row with
`ended_at IS NULL` — a former Driver's very next call fails ZW001,
same-session, same active token, the instant Operations reassigns
(work item §14/§8). Verified live through the real Dispatch UI (§34/§35
below).

--------------------------------------------------------------------
9. TERMINAL REVOCATION
--------------------------------------------------------------------
Once a Trip reaches any terminal state, the active assignment (closed as
a normal side effect of `cancel_trip`/`record_no_show`/
`driver_complete_trip`, all unchanged this phase) no longer exists, so
`_lock_driver_active_assignment()` returns null and the next post fails
ZW001 — additionally, `driver_get_trip_detail` itself (unchanged,
P1-E2-S3) independently requires a currently-active assignment, so the
Driver Trip Detail PAGE becomes fully inaccessible ("Trip unavailable")
before the tracker component even has a chance to render, an even
stronger revocation guarantee than the RPC alone (work item §15/§61).
Verified live (§36 below).

--------------------------------------------------------------------
10. COORDINATE VALIDATION
--------------------------------------------------------------------
`latitude` [-90,90], `longitude` [-180,180], `accuracy_meters >= 0` or
null — both a CHECK constraint (defense in depth) and an explicit
in-function check (raises the clean ZW006 rather than a raw
constraint-violation message). Verified live: TEST LOC-K (latitude 95.0
rejected), LOC-L (longitude -200.0 rejected), LOC-M (accuracy -5.0
rejected) — all ZW006, no row created.

11. TIMESTAMP AUTHORITY
--------------------------------------------------------------------
`recorded_at` is always the server's own `now()` — no `p_recorded_at`
parameter exists at all (ZD-163, a deliberate simplification beyond the
work item's own "validate it's not absurdly future-dated" baseline ask).

--------------------------------------------------------------------
12. DRIVER TRACKER ARCHITECTURE
--------------------------------------------------------------------
`src/components/driver/DriverLocationTracker.tsx` — isolated geolocation
side effects (work item §46): permission state, `watchPosition`
lifecycle, submission throttling, cleanup, status display, all kept out
of the Active Trip page component itself. Status machine: not-started →
requesting → sharing / denied / unavailable / stopped. Mounted by the
parent page ONLY while `trip.state` is in
`ELIGIBLE_LOCATION_TRACKING_STATES` — unmounting (Trip becomes terminal,
or the page itself becomes inaccessible after reassignment) is itself a
cleanup trigger, on top of the server's own independent checks.

--------------------------------------------------------------------
13. PERMISSION UX
--------------------------------------------------------------------
Permission requested only from an explicit "Share My Location" tap on
the Active Trip screen itself — never at sign-in, launch, or
automatically on mount (work item §17). Purpose stated concisely in the
surrounding status text. No separate modal interrupts the flow.

--------------------------------------------------------------------
14. BROWSER/PWA LIMITATIONS
--------------------------------------------------------------------
Documented honestly in driver-location-architecture.md §17 — foreground-
only reliability, mobile-browser throttling, no reliable
locked-screen/background tracking, iOS-specific constraints, no claim of
"continuous background GPS." A native migration path is documented as a
future requirement (§22 of that document), not built.

--------------------------------------------------------------------
15. UPDATE CADENCE
--------------------------------------------------------------------
`watchPosition()` (not a fixed-interval `getCurrentPosition` poll) — the
browser decides when a new reading exists; the tracker accepts every
reading it's given.

--------------------------------------------------------------------
16. THROTTLING
--------------------------------------------------------------------
Actual server submission is throttled to at most once every 20 seconds
(`SUBMIT_THROTTLE_MS`, the restrained middle of the work item's own
10-30s suggested range) via a `lastSubmitAtRef` timestamp check inside
the position callback — a reading that arrives before the window elapses
is simply not submitted, never queued.

--------------------------------------------------------------------
17. WATCH CLEANUP
--------------------------------------------------------------------
`navigator.geolocation.clearWatch()` called on unmount (React `useEffect`
cleanup), and a guard (`watchIdRef.current !== null`) prevents starting a
second concurrent watch if "Share My Location" is somehow invoked twice.
Fatal errors (`PERMISSION_DENIED`) also clear the watch explicitly.

--------------------------------------------------------------------
18. MULTIPLE-TAB BEHAVIOR
--------------------------------------------------------------------
NOT coordinated across tabs — documented as a deliberate, explicitly-
permitted deferral (work item §49): each tab independently manages its
own permission/watch/throttle state. Backend correctness is unaffected
either way (each write is independently authorized; at most a modest
write-volume increase in the rare two-tabs-open scenario).

--------------------------------------------------------------------
19. NETWORK FAILURE BEHAVIOR
--------------------------------------------------------------------
A failed submission is silently dropped (`.catch()` with no rethrow,
`.finally()` resets the submitting guard) — no crash, no alarming error
shown, no unbounded `localStorage` queueing. The next `watchPosition`
reading simply tries again on its own schedule (work item §21/§22).

--------------------------------------------------------------------
20. OPERATIONS READ ARCHITECTURE

`getLatestLocationsByTrip()` (src/lib/operations/live-location.ts) —
direct RLS-scoped SELECT (`driver_location_updates_select_org_operations`,
organization_admin/dispatcher), explicit columns, no `select("*")`, no
service role, no generic location repository. Wired into
`getDispatchBoardData()` as a second, focused query scoped to only the
Trip ids already known to be in the eligible tracking window.
