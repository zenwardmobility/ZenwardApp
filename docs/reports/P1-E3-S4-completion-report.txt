3. QUERY ARCHITECTURE
--------------------------------------------------------------------
`src/lib/operations/todays-operations.ts` — `getTodaysOperations()`,
the server-side data-access boundary the work item explicitly asked
for (§51). Three real, organization-scoped, explicit-column queries,
no `select("*")`, no service role:

  1. Today's trips — `trips`, filtered by `scheduled_pickup_at`
     within the organization's own local "today"
     (`organizationDayBoundsUtc()`, `src/lib/operations/day-bounds.ts`
     — a UTC `[start, end)` range computed via the same `Intl`-offset
     technique `operationalDateKey` already established in P1-E3-S2C,
     extended from a single-instant comparison to a real range for a
     `gte`/`lt` filter). Embeds `passengers(display_name)` and
     `trip_assignments(ended_at, drivers(display_name),
     vehicles(label))` via the confirmed composite-FK relationships
     (`trips_passenger_id_organization_id_fkey`,
     `trip_assignments_trip_id_organization_id_fkey`,
     `trip_assignments_driver_id_organization_id_fkey`,
     `trip_assignments_vehicle_id_organization_id_fkey`). Feeds Needs
     Attention, Upcoming Trips, and the Completed-Today subset.
  2. Active trips — `trips` filtered by `state in (5 non-terminal
     states)`, DELIBERATELY NOT bounded to today's window (ZD-131) —
     an in-progress Trip is happening right now by construction;
     bounding it to "scheduled for today" would incorrectly hide a
     running-late Trip whose `scheduled_pickup_at` technically fell
     on the prior org-local day. Feeds Active Trips and the "active"
     summary metric.
  3. Today's activity — `trip_events`, filtered by `occurred_at`
     within the same org-local day bounds, embedding
     `trips(passengers(display_name))` via
     `trip_events_trip_id_organization_id_fkey`, ordered
     `occurred_at desc`, limited to 20. Feeds the Activity Log.

Every query is additionally filtered by `.eq("organization_id", ...)`
explicitly — never left to RLS alone to narrow, the same
defense-in-depth convention `getActiveMemberships()`
(`src/lib/auth/membership.ts`) already established. No new RPC was
built (GAP-8 explicitly recommends against one until real usage shows
a need) — every value is derived from the same three queries the
panels themselves need.

Embedded-relation typing follows `getActiveMemberships()`'s own
established defensive pattern (`unwrapOne<T>()`) — a to-one composite
FK can come back as either an object or a one-element array depending
on supabase-js's type inference, so every embed is unwrapped
defensively rather than assumed to be one shape.

4. PRESENTATION LAYER
--------------------------------------------------------------------
`src/lib/operations/presentation.ts` — a distinct module from
`src/lib/driver/trip-presentation.ts`, not a shared one: Operations
sees every Trip in the organization and has a genuine "unassigned"
concept a Driver never encounters (a Driver only ever sees Trips they
hold an assignment on). Small time-formatting helpers
(`formatOperationsTime`/`formatOperationsLongDate`) are deliberately
duplicated rather than imported from `driver/` to keep that module
boundary clean.

`operationsTripStatusLabel(state, hasActiveAssignment)` — the plain
lifecycle status shown in the Upcoming Trips STATUS column and the
Active Trips list: `scheduled` reads "Assigned" when an active
assignment exists, "Scheduled" when it doesn't (matching the
reference's own Anna Reed/Mary Collins rows exactly); the 5
non-terminal states collapse to the same bare "En Route"/"Arrived"
labels lifecycle-model.md §C already sanctions as a presentation
choice, reusing every label `TRIP_STATUS_MAP`
(`src/components/ui/TripStatus.tsx`) already anticipated before this
phase's code was written. This is intentionally DISTINCT from the
literal "Needs Assignment" label used only in the Needs Attention
panel's ISSUE column — conflating the two would duplicate a warning
badge as the primary status everywhere a Trip appears, which the
reference itself does not do.

`operationsEventLabel(eventType)` — humanizes the full, real
`trip_events.event_type` allow-list (the CHECK constraint's own 16
values, `supabase/migrations/20260830131200_trip_events.sql`) for the
Activity Log. Unrecognized values fall back to the raw string,
matching `driverTripStateLabel`'s established convention.

`UNION ALL` mixing untyped `null` literals with a concrete

be matched`, even though the same technique (bare `null` unioned with
a `timestamptz` branch) already worked in the adjacent, unmodified
P1-E3-S2C fixture block. Root-caused to Postgres's `unknown`-type
resolution across more than two `UNION ALL` branches, not chased
further once found — fixed unambiguously by casting every placeholder
to `null::timestamptz` explicitly rather than relying on inference.
Verified by running `supabase/seed.sql` directly against the local
Postgres container via `psql` after the fix — zero errors, all
`INSERT` statements succeeded.

REAL BUG FOUND AND FIXED DURING THIS VISUAL QA (not a hypothetical
review — caught only because an actual 768px screenshot was captured
and inspected, exactly why this gate requires real screenshots and
not component-inspection alone): the header's `SearchInput` was
hidden below the `lg` breakpoint via `hidden lg:block` passed as its
own `className` prop — but `SearchInput` forwards `className` only to
its inner `<input>`, not to its own outer wrapping `<div>` (which also
renders the magnifying-glass icon as a sibling element). The `<input>`
was correctly hidden; its wrapper and icon were not, producing a tiny
floating icon-shaped box with no input next to it at 768px. Fixed by
wrapping `<SearchInput>` in a plain `<div className="hidden
lg:block">` instead (ZD-135). Re-captured the same screenshot after
the fix and confirmed the icon-leak is gone; re-ran the full
functional/security matrix (section 10) afterward to confirm the fix
introduced no regression — still 17/17 PASS.
