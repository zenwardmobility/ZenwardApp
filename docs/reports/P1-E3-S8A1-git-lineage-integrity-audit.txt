16. ROOT CAUSE OF THE HEAD CONTRADICTION
--------------------------------------------------------------------
**Root cause: A — the P1-E3-S8A completion report's own "Git HEAD before
work" metadata line was factually wrong; the repository's actual
lineage is, and was, correct throughout.**

Evidence ruling out the other candidate causes:
  - **B (stale/reset HEAD, retained working-tree diff):** Ruled out.
    The reflog (§7) contains zero `reset` entries of any kind, ever, in
    this repository's entire history. If HEAD had ever been reset to
    6357a47 and then moved back, the reflog would show it — Git's reflog
    records every ref update, including resets, and cannot be silently
    skipped by ordinary use. It shows none.
  - **C (repository reset/rebased/checked out backward):** Ruled out
    for the identical reason — no `rebase`, `checkout` (to a different
    ref), or forced-update entry exists in the reflog. The commit graph
    itself (§6) is also perfectly linear with no rewritten history
    (rebasing would produce different commit SHAs than the ones this
    audit — and every prior phase's own report — has consistently
    referenced by identical hash across sessions).
  - **D (another repository/worktree used accidentally):** Ruled out.
    `pwd` and `git rev-parse --show-toplevel` agree exactly (§1); there
    is only one `.git` directory in play, and its content (§8-§11)
    correctly contains every phase's own real, previously-verified work.
  - **E (some other cause):** No other anomaly was found in any command
    run for this audit.

The actual explanation: P1-E3-S8A's own report-writing step recorded the
wrong commit SHA/message in its header — `6357a47` "Implement Today's
Operations dashboard" is a real commit, but it is FOUR commits behind
the true pre-work HEAD (`e6c8377`), and was never the repository's
actual HEAD during or before S8A's own work session. No git command run
during S8A's actual work (confirmed by the reflog having no entries
between `e6c8377`'s own commit and now) would have produced 6357a47 as a
result — it was a transcription/authoring mistake in the report text
itself, not a symptom of any real repository operation. This is the same
CLASS of error — a report-metadata mistake, not a code or security
defect — as the P1-E3-S7B "33 vs 32 assertion count" finding earlier in
this project's own history: a documented artifact of report-writing,
independently caught and corrected by a later, dedicated audit phase,
exactly as intended by this project's own recurring "trust nothing,
verify from raw evidence" discipline.
