--------------------------------------------------------------------
P1-E3-S2A found (fixing the sign-in card only) that `max-w-sm` compiled
to `max-width: var(--spacing-sm)` = 8px instead of Tailwind's intended

custom `--spacing-sm` token for gap/padding use. This phase's job was
to determine whether that was a one-off or systemic, and fix it at the

3. AFFECTED CUSTOM TOKENS
--------------------------------------------------------------------
Every named key in the project's spacing scale collides with a
same-named key in Tailwind's own built-in `--container-*` scale
(`node_modules/tailwindcss/theme.css`, confirmed by direct inspection):

| Project token (was) | Value | Tailwind's `--container-{key}` |
|---|---|---|
| `--spacing-2xs` | 0.125rem | `--container-2xs: 18rem` |
| `--spacing-xs` | 0.25rem | `--container-xs: 20rem` |
| `--spacing-sm` | 0.5rem | `--container-sm: 24rem` |
| `--spacing-md` | 1rem | `--container-md: 28rem` |
| `--spacing-lg` | 1.5rem | `--container-lg: 32rem` |
| `--spacing-xl` | 2rem | `--container-xl: 36rem` |
| `--spacing-2xl` | 3rem | `--container-2xl: 42rem` |
| `--spacing-3xl` | 4rem | `--container-3xl: 48rem` |
| `--spacing-4xl` | 5rem | `--container-4xl: 56rem` |

All 9 project spacing keys collide — not just the 4 (sm/md/lg/xl)
P1-E3-S2A had directly observed. `2xs`/`xs`/`2xl`/`3xl`/`4xl` had no
real `max-w-*` consumer in the codebase at audit time (§5), so their
breakage was latent, not yet visibly manifested — but exactly as real
a defect, and left unfixed would have silently bitten the first future
use of `max-w-xl`/`max-w-2xl`/etc.

**Mechanism, confirmed empirically, not guessed:** Tailwind v4's
`max-width`/`min-width` utilities resolve a named key (`sm`, `md`, …)
by checking the shared `--spacing-*` namespace (the same namespace
`gap-*`/`p-*`/`m-*`/etc. use) as well as their own dedicated
`--container-*` namespace, and prefer a same-named `--spacing-*` entry
when the project has defined one. Stock, unmodified Tailwind v4 has no
named `--spacing-{key}` entries at all (only a single `--spacing:
0.25rem` base multiplier for numeric utilities like `p-4`) — this
collision exists ONLY because this project added its own named
`--spacing-sm`/`-md`/etc. keys that happen to share Tailwind's
reserved container-scale vocabulary. Confirmed directly from the
compiled CSS bundle both before and after: `max-w-5xl`/`max-w-6xl`
(sizes the project never defined a colliding `--spacing-*` entry for)
correctly used `--container-5xl`/`--container-6xl` throughout, proving
the mechanism precisely.

6. CHOSEN DURABLE FIX
--------------------------------------------------------------------
Renamed every custom spacing key from `--spacing-{key}` to
`--spacing-zw-{key}` in `src/app/globals.css` (numeric values
unchanged), and mechanically updated all 36 real consumers to the
`zw-` prefixed class name (`gap-md` → `gap-zw-md`, `p-lg` → `p-zw-lg`,
etc.). This keeps the tokens under Tailwind's genuinely-intended
`--spacing-*` namespace (so `gap-*`/`p-*`/`m-*` utility generation
keeps working automatically, unlike moving to an entirely different
CSS-variable prefix, which would have required manually re-declaring
every utility with `@utility` or falling back to verbose arbitrary-
value syntax everywhere) while making the *key* itself permanently
un-collidable with Tailwind's reserved container/size vocabulary —
`zw` is not, and will never be, a t-shirt-size word Tailwind defines.
`max-w-*`/`min-w-*` (and any future utility that shares the
`--spacing-*` fallback behavior) now resolve exclusively against
Tailwind's own scale, with nothing in this project able to shadow it,
for any of the 9 renamed keys or any future one. Recorded as ZD-117.

Explicitly not done: no per-usage arbitrary-value patching (rejected —
work item §4 explicit instruction, and it would have left the root
collision live for the next person to rediscover); no deletion of the
custom spacing scale (rejected — 36 real, working consumers depend on
it, per work item §3's explicit caution).
