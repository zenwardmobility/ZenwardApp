1. EXACT ROOT CAUSE
--------------------------------------------------------------------
`src/app/sign-in/page.tsx`'s auth card used `max-w-sm` (intended: ~24rem
/384px). The actual compiled CSS shows:

    .max-w-sm {
      max-width: var(--spacing-sm);
    }

`--spacing-sm` is a project-defined design token (`src/app/globals.css`
`@theme` block) equal to **0.5rem (8px)**, added for gap/padding use —
not a width scale. Confirmed empirically by fetching and inspecting the
compiled Next.js CSS bundle directly (not guessed):

- `.max-w-sm { max-width: var(--spacing-sm) }`  → 8px
- `.max-w-md { max-width: var(--spacing-md) }`  → 16px
- `.max-w-xl { max-width: var(--spacing-xl) }`  → 32px
- `.max-w-5xl { max-width: var(--container-5xl) }` → 64rem (correct)
- `.max-w-6xl { max-width: var(--container-6xl) }` → 72rem (correct)

Tailwind v4 ships its own, separate `--container-sm: 24rem` token (
confirmed by reading `node_modules/tailwindcss/theme.css:336` directly)
specifically so `max-w-*` utilities don't collide with a project's own
spacing scale. `max-w-5xl`/`max-w-6xl` correctly resolve via that
`--container-*` namespace here, because this project's `@theme` block
never defines a competing `--spacing-5xl`/`--spacing-6xl`. But this
project's `@theme` block DOES define `--spacing-sm`/`-md`/`-lg`/`-xl`
(0.5rem/1rem/1.5rem/2rem — the design system's own gap/padding scale),
and for exactly those four key names, Tailwind's engine resolves
`max-w-{key}` against the project's own `--spacing-{key}` instead of
its built-in `--container-{key}` default. **This is a real, systemic
Tailwind v4 theme-token naming collision affecting every `max-w-sm`/
`max-w-md`/`max-w-lg`/`max-w-xl` usage in this codebase**, not
something specific to the sign-in page's own markup.

With the card's actual max-width at 8px, every descendant that DOES
correctly fill its parent (the `<form>`, the `Button`, the block-level
`<h1>`/`<p>`) rendered at ~8px-wide, forcing every line of text to wrap
character-by-character and the whole card to appear as a "vertical
strip" — exactly the reported symptom. This was confirmed visually,
not just theoretically: a real headless-Chrome screenshot of the page
before any fix (`/tmp/signin_qa/before_desktop.png`, this session)
shows precisely the reported symptoms, button/labels overflowing past
the collapsed card edge into the dark background.

A second, smaller, independently real defect was also found and fixed:
the `<input>` element inside the shared `Input` component
(`src/components/ui/Input.tsx`) had no `w-full`/width class at all —
relying entirely on implicit flex-stretch behavior, which is not
reliably applied to native form controls in every browser/reset
combination. This did not fully explain the "narrow vertical strip"
on its own (the max-w-sm collision was the dominant cause — the card
itself was 8px regardless), but it is a real, separately worth-fixing
omission per the work item's own explicit "child missing w-full"
candidate-cause list, and is now fixed.

**What was NOT done:** the shared `--spacing-sm/md/lg/xl` vs.
`--container-sm/md/lg/xl` collision in `globals.css` was **not**
fixed globally. That token collision affects every `max-w-sm/md/lg/xl`
usage anywhere else in the app (Operations panels, modals, etc. — not
audited here), and correcting the shared `@theme` block is a
wider-blast-radius change this narrow, sign-in-only work item does not
authorize ("This task is ONLY to fix and visually harden the Sign In
layout"). Recommended as a dedicated future design-token cleanup —
see §2 for exactly what to change if/when that phase happens.

  image (see §12).

  correct fix (a labeled form field should always fill its container).
- `src/components/auth/SignInForm.tsx` — added `w-full` to the
  `<form>` element and the field-group wrapper `<div>`, matching the
  work item's own "Expected conceptual structure" (§2: "w-full
  constrained auth card → full-width form fields/buttons") explicitly
  rather than relying only on implicit block/flex default behavior.

No other file was touched for the width fix. No design token

Supabase/auth code, no Driver Today code.

**Not fixed, deliberately, for a future phase:**
