1. ORIGINAL STALE-REASSIGNMENT BEHAVIOR
--------------------------------------------------------------------
`reassign_trip` (as built in P1-E2-S2, unchanged through P1-E3-S5) had
no precondition tying a reassignment to the SPECIFIC `trip_assignments`
row a Dispatcher actually reviewed. It located whichever assignment was
currently active (`ended_at IS NULL`, under a row lock) and, if the
requested driver/vehicle differed from it, atomically closed it and
opened a new one — regardless of what the calling Dispatcher's own UI
last displayed.

--------------------------------------------------------------------
2. RISK
--------------------------------------------------------------------
Scenario: Dispatcher A opens a Trip currently assigned to Driver 1.
Dispatcher B reassigns the same Trip to Driver 2. Dispatcher A, unaware,
submits their own (by-then-stale) decision — say, to Driver 3. Under
the original behavior, A's request would succeed, silently overwriting
B's newer decision, with no indication to either dispatcher that a
conflict had occurred. Not a data-integrity risk (the schema's partial
unique index and the RPC's own row lock already guaranteed exactly one
active assignment at all times — confirmed transactionally safe in
P1-E3-S5's own concurrency testing) but a real operational one: two
dispatchers could each believe their own decision was final.

--------------------------------------------------------------------
3. RPC SIGNATURE BEFORE
--------------------------------------------------------------------
`reassign_trip(p_trip_id uuid, p_driver_id uuid, p_vehicle_id uuid
default null, p_reason text default null)`

--------------------------------------------------------------------
4. RPC SIGNATURE AFTER
--------------------------------------------------------------------
`reassign_trip(p_trip_id uuid, p_driver_id uuid, p_vehicle_id uuid
default null, p_reason text default null, p_expected_assignment_id
uuid default null)` — the new parameter appended at the end, matching
the work item's own preferred shape. Declared with a default of `null`
(required by Postgres parameter-ordering rules, since it follows two
already-defaulted parameters) but treated as functionally REQUIRED for
any real reassignment — a `null`/omitted value cannot bypass the check;
it is compared via `IS DISTINCT FROM`, under which NULL is never
"equal" to a real assignment id, so omitting the parameter fails
exactly the same way a wrong value does.

--------------------------------------------------------------------
5. SQL LOCKING/PRECONDITION MECHANISM
--------------------------------------------------------------------
`supabase/migrations/20260901120000_reassignment_concurrency_
hardening.sql`. Within the SAME transaction and the SAME row lock the
function already held for every other check (`select ... for update`
on both the Trip and the active `trip_assignments` row — no new lock,
no second round trip):
  1. Auth/role/state checks — UNCHANGED.
  2. Lock the active assignment (`ended_at is null ... for update`).
  3. No active assignment → `ZW005` (unchanged).
  4. Requested driver+vehicle already match the active assignment →
     idempotent no-op (`changed: false`), returned immediately —
     checked BEFORE the new precondition, deliberately (see §6).
  5. **NEW:** `if v_existing.id is distinct from
     p_expected_assignment_id then raise 'assignment_conflict' using
     errcode = 'ZW005'; end if;` — a real change is being requested;
     verify the caller reviewed the assignment that is STILL active.
  6. Driver/vehicle validation — UNCHANGED.
  7. Close old row, insert new row, write `trip_events`/`audit_events`
     — UNCHANGED, still one atomic transaction.
`assign_trip` was NOT modified (work item §8) — its existing "no
active assignment allowed" precondition already correctly rejects a
second, stale assignment attempt (re-verified, §17).
