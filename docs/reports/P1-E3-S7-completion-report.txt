--------------------------------------------------------------------
create_trip(
  p_organization_id uuid,
  p_passenger_id uuid,
  p_pickup_description text,
  p_destination_description text,
  p_scheduled_pickup_at timestamptz default null,
  p_appointment_at timestamptz default null,
  p_pickup_facility_id uuid default null,
  p_destination_facility_id uuid default null,
  p_assistance_notes text default null,
  p_instructions text default null,
  p_request_id uuid default null
) returns trip_creation_result (trip_id, organization_id, state, created)

Read directly from 20260831120000_controlled_trip_creation.sql and
confirmed identical in database.types.ts's generated `Args` type. `state`
is a fixed literal `'scheduled'` inside the function body — not a
parameter at all, structurally impossible for any caller to override
(work item §8/§9, unchanged this phase). Raises exactly 3 distinct ZW
codes: ZW001 (no session), ZW002 (not Organization Admin/Dispatcher for
this org), ZW006 (every other validation failure — address, Passenger,
Facility, Request, or time-ordering — all collapsed into one code by the
function itself).

16. LOCAL→UTC CONVERSION MECHANISM
--------------------------------------------------------------------
One explicit boundary: `organizationLocalToUtc()`
(src/lib/operations/local-time.ts), called server-side in
`createTripAction`. Reads the zone's standard and daylight UTC offsets
from two FIXED reference instants (Jan 1 / Jul 1 of the requested date's
own year, noon UTC) — never a hardcoded offset, never manual DST
arithmetic, every offset read live from `Intl`/the IANA tzdata (same
underlying data source `is_valid_iana_timezone` validates against at the
database layer, P1-E3-S2C). For each of the (at most 2) distinct offsets,
computes a candidate UTC instant and checks whether formatting it back in
the organization's timezone reproduces the EXACT requested wall-clock
fields:
  - exactly one candidate round-trips → `{status: "ok", utc}` (the
    ordinary case)
  - zero candidates round-trip → `{status: "nonexistent"}` (spring-
    forward gap)
  - two distinct candidates both round-trip → `{status: "ambiguous"}`
    (fall-back repeated hour)
This was unit-verified against 8 hand-computed cases (ordinary EST,
ordinary EDT, spring-forward gap, fall-back ambiguity, midnight crossing,
America/Chicago, UTC/no-DST, an ordinary February date) before being
wired into the application, then re-verified end-to-end through the real
UI (§39-§42 below).

--------------------------------------------------------------------
17. DST HANDLING
--------------------------------------------------------------------
Both edge cases are explicitly detected and rejected BEFORE `create_trip`
is ever called, with an honest, specific error ("That date and time
couldn't be resolved in the organization's timezone (it may fall in a
daylight-saving change). Choose a different time.") — never a silently-
guessed instant. Documented limitation: the two-offset-probe technique
assumes at most 2 distinct UTC offsets within a calendar year (true for
every US IANA zone, including both this product's current organizations —
America/New_York, America/Chicago); a future organization in an
exotic zone with more than 2 offset changes per year is out of this
implementation's verified scope (recorded as ZD-157's own review
trigger, not silently overclaimed).

69. DISCREPANCIES FOUND
--------------------------------------------------------------------
A real functional bug, found via this phase's own genuine browser
testing (not visual — it never rendered incorrectly, it logged a React
warning): `Select` (src/components/ui/Select.tsx) unconditionally set
`defaultValue` whenever a `placeholder` prop was given, even when the
caller ALSO passed a controlled `value` — "Select elements must be either
controlled or uncontrolled." This is the first place in the codebase a
`Select` is both controlled (`value={state}`) AND given a `placeholder` —
every prior usage (`AssignmentDialog`) was uncontrolled, so the defect
was latent and never triggered before this phase's own new usage pattern.

--------------------------------------------------------------------
70. DISCREPANCIES CORRECTED
--------------------------------------------------------------------
Fixed at the component level (not worked around per-callsite): `Select`
now only sets `defaultValue` when the caller has not passed a controlled
`value`. Re-verified: the console warning is gone, and every controlled
Select on this page (Passenger, Pickup/Destination Facility, Transportation
Request) behaves correctly (auto-select-on-add, auto-fill-on-facility-
select, import-on-request-select all depend on this being genuinely
controlled). This is a systemic fix — any future controlled-`Select`-with-
placeholder usage benefits from it.
