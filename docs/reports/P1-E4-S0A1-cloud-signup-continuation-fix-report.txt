2. REPRODUCING THE REPORTED CLOUD FAILURE
--------------------------------------------------------------------
Read the actual current source (not assumed from docs) for the full
signup path: `/sign-up`'s Server Action, `/join/[token]`'s Server
Action, `signup_create_organization`, root `/` routing, and
`/access-unavailable`. Found the exact mechanism, confirmed by
tracing the code (not by asking the deployed app, which required a
real inbox and rate-limited email — see §8):

`src/app/sign-up/actions.ts` called `signUp({ email, password })`
with NO metadata. `fullName`/`businessName` existed only as local
variables inside that one Server Action invocation. When Supabase
Auth requires email confirmation, `signUp()` returns no session — the
action returned `needsEmailConfirmation: true` and those two values
were gone, never persisted anywhere. The person who later confirms
their email and signs in reaches `/` with a real session and zero
Memberships → `resolveOrganizationContext()` returns `status: "none"`
→ (before this phase) straight to `/access-unavailable`, a dead end
offering only Sign Out. This exactly matches the reported failure —
confirmed as the root cause by reading the code, not inferred.

The same class of bug existed in `/join/[token]`'s Driver-invite
signup (§7 below): the invite `token` was likewise only a local
Server Action variable, lost the same way.

--------------------------------------------------------------------
3. ARCHITECTURE OF THE FIX
--------------------------------------------------------------------
Matches the work item's own preferred architecture:

  Supabase Auth signUp()
    → pending signup intent persisted in user_metadata (NOT authority)
    → email confirmation
    → HTTPS callback (Supabase's own /auth/v1/verify → Site URL)
    → authenticated completion route (Route Handler, not a page — §5)
    → UserProfile + Organization + organization_admin Membership
    → onboarding

**What's persisted, and why it's safe (work item §4 — "acceptable to
store non-sensitive onboarding intent... metadata is never
authorization"):** `signUp()`'s `options.data` now carries
`pending_full_name`/`pending_business_name` (operator signup, in
`src/app/sign-up/actions.ts`) or `pending_driver_invite_token`
(+`pending_full_name`) for Driver-invite signup, in
`src/app/join/[token]/actions.ts`. Supabase persists this on the
`auth.users` row itself (`raw_user_meta_data`), independent of
confirmation state. This is plain display/intent data — the role
granted (`organization_admin`, always) and the actual Organization/
Membership identity are still derived entirely server-side from
`auth.uid()` inside SECURITY DEFINER RPCs. Metadata is READ to decide
WHICH RPC to call; it never grants privilege by itself, and nothing
in this design trusts a client-supplied user_id, organization_id, or
role — full detail in `docs/product/operator-onboarding-model.md`
§4A and `docs/product/driver-invite-linkage-model.md` §1A.

--------------------------------------------------------------------
4. ROOT CAUSE OF WHY FULL NAME/BUSINESS NAME/INTENT WERE LOST
--------------------------------------------------------------------
See §2. The precise mechanism: `signUp()`'s local-variable-only
values never survive past the single Server Action invocation that
received them, and no other code path ever reads them again. Fixed
by moving them onto Supabase's own persistent `auth.users` row at the
moment of signup — the earliest point they can be captured, and a
storage location that survives the confirmation boundary by
construction (Supabase itself manages it, not this application).

5. THE CONTINUATION ROUTE — AND A REAL FRAMEWORK BUG FOUND BUILDING IT
--------------------------------------------------------------------
`/complete-signup` (`src/app/complete-signup/route.ts`) is the one
authoritative continuation point. Root `/` now routes every
authenticated, zero-Membership visitor here — not straight to
`/access-unavailable` — because a real session can come to exist
WITHOUT the person ever submitting `/sign-in`'s own form: Supabase's
confirmation-link redirect (`/auth/v1/verify` → Site URL) is exactly
that path. `requireOperationsAccess`/`requireOnboardingAccess`/
`requireDriverAccess`/`/select-organization` were ALSO updated
(`src/lib/auth/authorization.ts`, `src/app/select-organization/
page.tsx`) to route their own "zero Membership" cases through
`/complete-signup` first — closing the same gap for a deep link
(a bookmark, an already-open tab) reached before ever visiting `/`.

**A genuine Next.js App Router bug found and designed around, not
papered over:** an earlier version of this fix put the identical
routing/completion logic in a Server Component page
(`complete-signup/page.tsx`). Live local testing (a REAL Mailpit-
delivered confirmation email, a real link click, then sign-in — not
assumed) showed: the mutation (Organization/Membership creation)
succeeded server-side EVERY time, confirmed directly against the
database — but the page's own `redirect("/onboarding")` call,
issued from a chained client-router navigation after an internal
`await` for that mutating RPC, was silently not followed by the
browser. The on-screen URL stayed stuck at `/complete-signup`
indefinitely (verified via a 15-poll, 6-second wait — no change);
only a hard reload of that same URL then correctly redirected onward.
Fixed by moving the logic to a Route Handler (`route.ts`), which
always returns a real HTTP redirect response with a `Location`
header — the well-trodden path Next's client-side navigation
reliably follows. Recorded as ZD-200 (durable pattern for any future
similar flow).

A second, related issue found the same way: Next.js's OWN dev-mode
navigation fired two concurrent GET requests to `/complete-signup`
for one sign-in (observed directly in the dev server's request log).
Since `complete_pending_signup()` is idempotent, this created the
Organization/Membership exactly once regardless — but the FIRST
version of the destination logic ("did *this* request create it? →
onboarding, else → operations") meant the losing, second request
could redirect a genuinely brand-new owner straight to a bare
Operations screen, skipping onboarding entirely. Fixed by deciding
the destination from the organization's own `business_stage` (still
`null` only for a never-onboarded org) instead of from which request
happened to win the race — recorded as ZD-201. Re-verified after the
fix: the same race, reproduced again, correctly lands on `/onboarding`
from either request. Also verified this specific race is a dev-mode-
only Next.js characteristic — a production build (`next build` +
`next start`) was separately tested (§9) and reached `/onboarding`
directly, exactly once, with no stuck intermediate state.

6. IDEMPOTENCY — EXACTLY ONCE, NOT "WHICHEVER REQUEST GOT THERE FIRST"
--------------------------------------------------------------------
`signup_create_organization` is DELIBERATELY non-idempotent by its
own S9-era design (a second call is a legitimate second business —
unchanged, still true, still correct for that case). The
continuation therefore needed its OWN exactly-once gate, not a thin
wrapper: two new SECURITY DEFINER RPCs
(`supabase/migrations/20260903110000_complete_pending_signup.sql`):

  complete_pending_signup()
    - pg_advisory_xact_lock keyed by the caller's own auth.uid() —
      serializes concurrent calls from the SAME person (two tabs, a
      double sign-in, the dev-mode race in §5).
    - If the caller already holds ANY Membership → safe no-op
      (created: false). Covers every repeat call after the first
      success, and anyone who already has an org through another path.
    - Reads pending_full_name/pending_business_name from
      auth.users.raw_user_meta_data, calls signup_create_organization
      with them exactly once.

  complete_pending_signup_manual(full_name, business_name)
    - Same lock + Membership guard, caller-supplied values instead of
      metadata — backs the explicit recovery form (§9 below).

Both verified via 8 new SQL tests (SIGNUPCONT-1 through 8, in
`supabase/tests/operator_onboarding_tests.sql`) AND via live local
browser runs, including a genuine concurrent-request race (§5) —
Organization/Membership/UserProfile confirmed created EXACTLY ONCE
via direct database query in every run, never zero, never two.

7. DRIVER INVITE CONFIRMATION — AUDITED AND FIXED SEPARATELY
--------------------------------------------------------------------
`/join/[token]`'s `joinSignUpAction` had the identical bug: `token`
was only a local variable, lost the moment `signUp()` returned no
session. Fixed the same way — `options.data.pending_driver_invite_
token` (+ `pending_full_name`, for a parity fix below) persisted at
signUp() time. `/complete-signup` checks for this token FIRST, before

  - Present → calls `redeem_driver_invite(token)` (unchanged,

  - Failure (revoked/stale/wrong-email/any other denial
    `redeem_driver_invite` already enforces) → `/access-unavailable`
    — deliberately NEVER the operator organization-creation form.
    Verified structurally: the driver-invite branch returns before
    the operator-metadata branch is ever reached in the same request.

**A related, smaller, pre-existing gap found and fixed while
auditing this (not newly introduced):** `/join/[token]`'s own
pre-confirmation `user_profiles` upsert silently failed (no session
yet to satisfy `user_profiles_insert_own`'s self-only RLS check,
error never checked) — meaning a confirmed Driver invitee's
`user_profiles.display_name` stayed unset. `drivers.display_name`
itself (the Driver-facing source of truth, set from the admin's own
invite) was NEVER affected by this — confirmed by reading
`redeem_driver_invite`'s own INSERT, which sources `display_name`
from the invite row, never `user_profiles`. Fixed for parity anyway:
`/complete-signup`'s driver-invite branch retries the
