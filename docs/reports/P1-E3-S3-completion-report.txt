4. DRIVER ACTIVE TRIP ARCHITECTURE
--------------------------------------------------------------------
`src/app/driver/trips/[tripId]/page.tsx` — Server Component, reads
`driver_get_trip_detail(p_trip_id)` only. Any error or missing row
(malformed ID, nonexistent, foreign-org, never-assigned,

closed) renders the identical "Trip unavailable" `EmptyState` — no
existence oracle, matching ZD-095's established convention. On
success: passenger name + status badge, `DriverActiveTripLegs` (new
component — pickup/drop-off blocks with contextual Navigate/Call
Passenger), any `driver_notes` rendered via the existing
`DriverInstruction`, a Passenger Requirements `DefinitionList`
(Assistance/Instructions only — no Companion, no reference code — see
§21/§23), and the one primary lifecycle action
(`DriverLifecycleAction`, a Client Component wrapping a real `<form>`
+ Server Action).

10. STATE → ACTION MAPPING
--------------------------------------------------------------------

single centralized table, verified against both lifecycle-model.md §N

same transaction as any terminal transition), a Driver can never
actually be shown one of those three states via
`driver_get_trip_detail` in the first place.

11. LIFECYCLE MUTATION ARCHITECTURE
--------------------------------------------------------------------
One shared Server Action, `progressTripAction`
(`src/app/driver/trips/[tripId]/actions.ts`) — no service role, runs
under the caller's own session via `createServerSupabaseClient()`.
`rpc` is validated against a fixed allowlist derived from
`DRIVER_NEXT_ACTION` before ever being passed to `supabase.rpc()` —
never an arbitrary client-supplied function name. `requireDriverAccess()`
is re-derived fresh on every single call (never trusted from the
page's earlier render) — this is precisely what makes the
same-session inactive-Membership/inactive-Driver tests below pass.
`revalidatePath()` is called for the detail route, the Trips list, and
Driver Today after every successful mutation (work item §28). See
ZD-124 for the one genuine architectural finding this phase's own
testing surfaced (documented in full there and in §32 below).

13. IDEMPOTENT RETRY HANDLING

Verified directly (§33).

14. MUTATION ERROR MAPPING
--------------------------------------------------------------------
`src/lib/driver/errors.ts` — `mapDriverActionError()` translates the
PostgREST `error.code` field (confirmed empirically to be the literal
string `"ZW001"`/`"ZW002"`/`"ZW003"`, not a raw SQLSTATE — verified by
a live probe against the real local instance before writing the
mapping, not assumed) to one of 4 safe, stable application codes
(`UNAUTHORIZED`/`NOT_FOUND`/`STALE_STATE`/`UNKNOWN`), each with calm,
generic copy. No ZW-code, SQLSTATE, or Postgres/PostgREST message
ever reaches the rendered page — confirmed by direct code inspection
(the error object's `.message`/`.details`/`.hint` fields are never
read anywhere in the Driver code path).

--------------------------------------------------------------------
15. CONCURRENT/REASSIGNMENT BEHAVIOR
--------------------------------------------------------------------
On any mutation error (stale state, reassignment, lost access), the
client component calls `router.refresh()` exactly as it does on
success — the page's own `driver_get_trip_detail` call independently
re-derives current accessibility, naturally rendering either the
refreshed active-trip UI or "Trip unavailable." No separate
client-side "am I still authorized" logic was written — the database
remains the single source of truth. Verified end-to-end (§29 below):
Driver A's detail page genuinely showed "Trip unavailable" after a
real `reassign_trip` call moved the Trip to Driver B.
