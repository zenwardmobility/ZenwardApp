--------------------------------------------------------------------------------
1. SCOPE OF THIS PHASE
--------------------------------------------------------------------------------
Implement the controlled RPC/mutation layer that lets the application
actually move a Trip through its lifecycle, assign/reassign a Driver, and
record cancellation/no-show — every write happening through narrow,
transactional, SECURITY DEFINER PostgreSQL functions with a full
authorization chain, idempotent-retry semantics, row-level concurrency
protection, and atomicity, rather than through any direct table grant.

Explicitly out of scope and NOT done (per instruction, and confirmed by
`git status` below): no application/UI code touched, no public request
intake, no Driver→Passenger read projection, no remote Supabase link, no
commit/push, no .env/service-role/secret material created.

3. AUTHORIZATION CHAIN (every mutation RPC)
--------------------------------------------------------------------------------
auth.uid() present -> Trip exists & caller has real RLS-mirrored visibility
into it (ZW002 if not, uniformly for "doesn't exist" and "not yours" — no
existence oracle) -> idempotent-no-op check -> role/assignment-specific
permission for THIS action (ZW001 if visible-but-not-permitted) -> current
state legality (ZW003/ZW004) -> row-locked, atomic mutation -> TripEvent
(+AuditEvent where ZD-087 requires it) -> typed result.

Platform Admin is explicitly NOT a bypass anywhere in this chain (verified
directly, not merely asserted — see §5). Every check is live (Membership
status, Driver status, active-assignment state) — nothing is cached from a
JWT claim.

--------------------------------------------------------------------------------
4. CONCURRENCY, ATOMICITY, LOCKING
--------------------------------------------------------------------------------
Lock order fixed everywhere: trips row (FOR UPDATE) first, then the active
trip_assignments row if relevant (ZD-086) — uniform across all 10 RPCs,
which is what makes concurrent calls deadlock-free by construction rather
than "usually fine."

Atomicity was verified with an actual forced-failure test, not merely
asserted: a temporary trigger on audit_events raises an exception on
reassign_trip's LAST write (its own AuditEvent insert, after the
trip_assignments close+insert and the trip_events insert already ran).
Result: the entire call rolled back — original assignment still active
with its original driver, no new trip_assignments row, no new trip_events
row, no audit_events row. The temporary trigger was removed afterward; it
is not a permanent object.

Concurrency was verified with genuine two-process contention, not a
single-connection script: supabase/tests/mutation_concurrency_test.sh
drives two separate psql connections. Session A holds the Trip row lock
for ~2s inside an open transaction; Session B, launched ~0.3s later, calls
assign_trip on the same Trip. Measured result (this run): Session B's call
took 1.86s wall-clock (proving it genuinely blocked on A's lock, not a
lucky ordering), and once unblocked correctly observed A's already-
committed assignment and rejected with assignment_conflict (ZW005) rather
than racing past it — exactly one active trip_assignments row exists at
the end. The partial unique index (trip_assignments_one_active_per_trip,
from P1-E2-S1) remains the schema-level backstop underneath this.

One real bug was found and fixed during this phase's own development (not
a regression against prior work): `_driver_execute_trip_transition`
originally checked for a currently-active assignment BEFORE the idempotent-
no-op check, which meant a Driver retrying their own already-successful
`driver_complete_trip` call (whose FIRST call had legitimately closed the
assignment as part of completing) was wrongly rejected as unauthorized
instead of receiving the expected idempotent success. Fixed by reordering
the checks (ZD-090 records the corrected, intentional precedence) —
caught by mutation_lifecycle_tests.sql L7/L8 during development, not
discovered later.
