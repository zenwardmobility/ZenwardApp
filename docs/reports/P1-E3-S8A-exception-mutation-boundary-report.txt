--------------------------------------------------------------------
3. WHY THE EXISTING STATE WAS UNSAFE
--------------------------------------------------------------------
S8's own completion report (§6) had already identified, but not closed,
this exact gap: a legitimately authenticated Operations user could
bypass `report_trip_exception`/`resolve_trip_exception` entirely via a
raw PostgREST/Supabase-client table write, because the underlying direct
policies were left in place. Concretely:
  - `trip_exceptions_insert_operations` let an Operations actor set
    `created_by` to ANY user id (impersonation) and `status` to
    `'resolved'` directly (fabricated pre-resolved history).
  - `trip_exceptions_update_operations` had no column restriction: an
    Operations actor could rewrite `exception_type`/`description`/
    `created_by` on a resolved historical row, or set `status='open'`
    to silently reopen it.
"The UI doesn't call the direct mutation" is not a database-enforced
security boundary — this is the exact principle this phase closes the
gap against.

--------------------------------------------------------------------
4. INSERT BOUNDARY — BEFORE
--------------------------------------------------------------------
Two policies (`trip_exceptions_insert_operations`,
`trip_exceptions_insert_assigned_driver`) plus a table-level `insert`
grant to `authenticated`. Operations population unconstrained on
`created_by`/`status`; Driver population already narrow but reachable
directly, in parallel with the RPC.

--------------------------------------------------------------------
5. INSERT BOUNDARY — AFTER
--------------------------------------------------------------------
Both policies dropped. `insert` revoked from `authenticated` on the
table entirely. `report_trip_exception` (SECURITY DEFINER) is the sole
INSERT path for any actor, Operations or Driver.

--------------------------------------------------------------------
6. UPDATE BOUNDARY — BEFORE
--------------------------------------------------------------------
One policy (`trip_exceptions_update_operations`), org-scoped only, no
column restriction — could rewrite any field on any row in the caller's
org, resolved or not.

--------------------------------------------------------------------
7. UPDATE BOUNDARY — AFTER
--------------------------------------------------------------------
Policy dropped. `update` revoked from `authenticated` on the table
entirely. `resolve_trip_exception` (SECURITY DEFINER) is the sole UPDATE
path, and its own column set is narrow by construction (`status`,
`resolved_by`, `resolved_at`, `resolution_note` only — never
`exception_type`/`description`/`created_by`/`created_at`).

--------------------------------------------------------------------
8. DELETE BOUNDARY
--------------------------------------------------------------------
Never granted to `authenticated` by any migration, before or after this
phase. Verified explicitly (not left an unstated assumption) via a
direct bypass test (BND-C) and a foreign-org variant (BND-I-DELETE) —
both DENIED with `insufficient_privilege`.

--------------------------------------------------------------------
9. DRIVER DIRECT-WRITE DECISION
--------------------------------------------------------------------
Retired. `trip_exceptions_insert_assigned_driver` — even though it was
already independently narrow and safe — is dropped along with the two
Operations policies, so that ALL normal TripException creation goes
through the identical controlled RPC, for every actor type. Two
mutation surfaces for one logical action (Operations via RPC, Driver via
RLS) was rejected as an unnecessary maintenance/reasoning burden with no
compensating benefit, per work item §6's own stated preference.

--------------------------------------------------------------------
10. DRIVER AUTHORIZATION — BEFORE
--------------------------------------------------------------------
`is_driver_assigned_to_trip(p_trip_id)` — a READ-scope check (built in
P1-E2-S1 for read-access purposes) meaning "has this Driver EVER had an
assignment on this Trip, active or historical." A reassigned-away or
post-terminal Driver could still successfully call
`report_trip_exception`.

--------------------------------------------------------------------
11. DRIVER AUTHORIZATION — AFTER
--------------------------------------------------------------------
`_lock_driver_active_assignment(p_trip_id, p_organization_id)` — the
same WRITE-scope, currently-active-assignment-only primitive
`driver_record_location` already uses (P1-E3-S7A). Returns a
null-fielded row (checked via `.id is null`) if the calling user has no
active `trip_assignments` row on this Trip in this org — covering wrong
org, no Driver row, inactive Driver/Membership (`current_driver_id`'s
own ZD-100 correction, inherited transitively), never assigned, and
reassigned-away, all collapsing to the identical `ZW002`, no existence
oracle.

--------------------------------------------------------------------
12. CURRENT-ASSIGNMENT REQUIREMENT — TERMINAL-STATE REASONING
--------------------------------------------------------------------
No separate explicit "Trip is not terminal" branch was added. Verified
directly by reading `driver_complete_trip`, `cancel_trip`, and
`record_no_show`'s own bodies (`20260831100200_controlled_trip_
mutations.sql`): all three close the Trip's active `trip_assignments`
row (`ended_at = now()`) in the SAME transaction as the terminal state
change. Requiring a currently-active assignment is therefore already
structurally sufficient to exclude every terminal Trip. A separate check
was considered and rejected: placed after the assignment check it would
be unreachable dead code; placed before it, it would leak a foreign-org
Trip's terminal/non-terminal status to a caller with no proven
relationship to it — an existence-oracle leak, the exact class of defect
this codebase's `ZW002`-everywhere convention exists to prevent. See
ZD-178 for the full decision record.
