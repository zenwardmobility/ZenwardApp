1. BEHAVIOR BEFORE AUDIT
--------------------------------------------------------------------------------
`_driver_execute_trip_transition` (the shared internal executor behind all 6
`driver_*` RPCs) granted its idempotent no-op success whenever:

  (a) the Trip's current state already equalled this function's target
      state, AND
  (b) the calling Driver satisfied `is_driver_assigned_to_trip` — i.e. had
      EVER (historically) held a `trip_assignments` row on this Trip.

Condition (b) does not distinguish "I am the Driver who performed this
exact transition" from "I am A Driver who once had some assignment on this
Trip, performed by someone else entirely." Two different Drivers can each
satisfy `is_driver_assigned_to_trip` on the same Trip (one historical, one
current). This meant a formerly-assigned Driver, retrying an action that a
DIFFERENT Driver had actually performed after a reassignment, would
receive a false idempotent success — `changed: false`, current_state
correctly reported, but the caller was never the legitimate actor.

This gap was NOT caught by the P1-E2-S2 test suites. Those suites tested
"the actual completer retries their own successful call" (required
behavior, correctly passing) and "a Driver who was never assigned at all"
(correctly denied, since `is_driver_assigned_to_trip` alone already blocks
that case) — but never the specific combination this audit targets: a
Driver who WAS once assigned, but is retrying an action a DIFFERENT actor
performed.

3. GAP FOUND: YES
--------------------------------------------------------------------------------
Confirmed, not merely reasoned about. Before writing the fix, the original
(pre-fix) idempotency logic was reproduced exactly under a temporary,
non-persistent test-only function (`_test_old_vulnerable_driver_transition`,
created, exercised, and dropped in the same session — never a permanent
object, never touching the real corrected function) and run directly
against case B's exact fixture state:

  Driver A1 (formerly assigned, never performed arrived_at_pickup on this
  Trip; Driver A2 actually performed it) called the OLD logic for
  driver_arrive_at_pickup:

    old_logic_result_case_b
    ------------------------------------------------------------------
    (90000000-0000-0000-0000-0000000000b3, arrived_at_pickup,
     arrived_at_pickup, changed=false)

  i.e. the old code returned a clean SUCCESS to Driver A1 for an action
  they never performed — the exact false-positive this audit was
  commissioned to find. This is empirical confirmation, not a hypothetical.

Severity: Driver-facing, not Passenger/tenant-data-facing. The false
success does not let a Driver mutate anything they could not otherwise
already have observed via RLS SELECT (the Trip's true current state was
never misreported — `current_state` in the false-success response was
accurate), and it grants no elevated read access. Its impact is a false
positive on the ACTION-authorization boundary specifically: an
unauthorized-to-act Driver could believe (and have their client believe)
they successfully performed an action they did not, in a scenario that
requires a genuine prior reassignment to construct. No exploitation of
this gap occurred in this local, fictional-data-only environment; it was
found by design review before this code was committed, deployed, or
exposed to any real client.

4. IMPLEMENTATION CHANGE
--------------------------------------------------------------------------------
`_driver_execute_trip_transition`'s idempotent no-op branch now requires,
in addition to "Trip already at target state":

  exists (
    select 1 from public.trip_events
    where trip_id = p_trip_id
      and event_type = p_event_type
      and actor_user_id = auth.uid()
  )

i.e. trusted, append-only proof — from the same `trip_events.actor_user_id`
column every mutation function already writes — that THIS caller
(resolved via `auth.uid()`, never a caller-supplied value) is the one who
actually performed this exact transition. Every event_type in this
transition set is written at most once per Trip (transitions are strictly
forward, terminal states never revisited), so the lookup is unambiguous —
no ordering or LIMIT concerns.

A caller who fails this check falls through to the pre-existing active-
assignment requirement, which correctly denies them (ZW001) — a caller in
that branch can never still hold the Trip's active assignment either (if
they did, they would be the one who performed the transition and would
already have matched the actor check above), so the fallthrough is safe
by construction, not merely by the immediate test results.

No caller-supplied actor id was introduced anywhere, per instruction.
`cancel_trip`, `record_no_show`, `assign_trip`, and `reassign_trip` were
reviewed and deliberately NOT changed — their authorization is live-
checked, org-scoped role (`has_org_role`), not trip-instance-specific
personal identity, so no analogous gap exists there: any currently-
authorized Organization Admin/Dispatcher may legitimately re-assert an
already-true org-level fact (e.g. retry cancelling a Trip a colleague
already cancelled), which is intended behavior, not a security gap.

6. ZD-090 STATUS
--------------------------------------------------------------------------------
ZD-090 is AMENDED, not superseded. Its core guarantee — that the target-
state-already-holds check takes precedence over the active-assignment
requirement, so a Driver can retry their own already-successful call even
after their assignment is later closed — remains correct and unchanged
(confirmed by test E). A new decision, ZD-093, clarifies and tightens the
no-op's own eligibility test: it must be actor-verified via trusted
TripEvent history, not merely "the caller has some historical relationship
to this Trip." Both decisions now appear in docs/product/decision-
register.md; docs/data/mutation-api.md and docs/security/mutation-
authorization.md were updated to describe the corrected behavior and
reference the new decision.

9. REMAINING RISKS
--------------------------------------------------------------------------------
- The fix's correctness depends on the invariant "each event_type is
  written at most once per Trip." This holds today because the Trip state
  machine is strictly forward and terminal states are never revisited
  (verified structurally, not merely assumed — `_is_valid_trip_transition`
  is the single source of truth for legal edges and permits no cycle back
  to an already-visited state). Any FUTURE change that allowed a state to
  be re-entered (e.g. an "un-cancel" or "reopen" action, explicitly not
  built and not requested) would need to re-examine this assumption before
  reuse, since a `trip_events` lookup with no ordering/LIMIT would then
  need revisiting. Flagged for future reviewers, not a present gap.
- Ops-family functions (`cancel_trip`/`record_no_show`/`assign_trip`/
  `reassign_trip`) were deliberately left unchanged, reasoned through in
  §4 above as not sharing this vulnerability shape. This reasoning was not
  independently re-verified with a dedicated adversarial test suite the
  way the Driver family was in this audit (out of this audit's stated
  scope) — a future audit could add explicit "does the same-org, wrong-
  original-actor idempotent-retry case exist for ops functions" tests as
  a confirming regression guard, though the authorization-model reasoning
  (org-scoped role, not trip-instance-specific identity) is sound.
- This audit did not re-examine `assign_trip`/`reassign_trip`'s own
  idempotent-match branches (content-based: matching driver_id/vehicle_id
  against the currently active row) for an analogous actor-identity
  question, since those checks were never actor-based to begin with (see
  §4) — noted here for completeness, not because a gap is suspected.
