MAIN FINDING — proxy.ts was never actually running, at the project
root, in this project, since it was first built in P1-E3-S1:

This phase's own verification work initially reproduced what looked
like two separate Next.js-level bugs while auditing the rename:
(a) an apparent Turbopack dev-mode failure to invoke the handler at
    all (proven via a temporary __proxy_test__ short-circuit response
    that returned a normal page instead, in dev mode), and
(b) the x-zw-pathname header (used by requireOperationsAccess /
    requireDriverAccess to build a precise `next=` redirect target
    for nested routes) never reaching Server Components' headers(),
    in BOTH dev and production mode — confirmed via a temporary
    debug page dumping all headers seen server-side, and via curl:
    an unauthenticated request to /operations/dispatch redirected to
    /sign-in?next=%2Foperations (the parent fallback) instead of the
    precise /sign-in?next=%2Foperations%2Fdispatch.

Continued investigation (this is a compatibility phase; a genuine
behavioral gap discovered while verifying the very thing this phase
is about was treated as in-scope to run down, not something to file
away on first appearance) traced both symptoms to a single, simpler
root cause by reading Next.js's own build source directly
(node_modules/next/dist/build/index.js and
node_modules/next/dist/lib/find-pages-dir.js):

  appDir = findDir(dir, "app")        // = <project>/src/app, since
                                       //   this project uses a src/
                                       //   layout
  rootDir = path.join(appDir, "..")   // = <project>/src
  // the build then scans ONLY the top level of rootDir (non-
  // recursively — confirmed via node_modules/next/dist/lib/
  // get-files-in-dir.js, which uses fs.opendir with no recursion)
  // for a file named middleware.* or proxy.*

Because rootDir resolves to <project>/src (not <project>/, the true
repository root) whenever the app router lives under src/app, a
proxy.ts (or, before this phase, middleware.ts) placed at the true
project root sits ONE DIRECTORY OUTSIDE the directory the build
actually scans, and is silently never found — no error, no warning,
just an empty middleware-manifest.json and no "ƒ Proxy (Middleware)"
line in the build summary. This matches Next.js's own documented
placement rule ("the same level as pages or app, or inside src if
applicable") — for a src/app project, that means src/proxy.ts, not a
true-root proxy.ts.

8. COOKIE SECURITY SETTINGS (zw_org_context)
--------------------------------------------------------------------
Set in src/app/select-organization/actions.ts:

  httpOnly: true
  sameSite: "lax"
  secure: process.env.NODE_ENV === "production"
  path: "/"
  maxAge: 60 * 60 * 24 * 30   (30 days)

`secure` is conditional on NODE_ENV so local HTTP development remains
usable (work item §7's explicit "do not make localhost development
unusable"), while any production deployment served over HTTPS gets
secure=true automatically with no separate flag to remember to flip.
No changes were made to this in P1-E3-S1A — it was already correct
as built in P1-E3-S1. Per its own design (documented in
docs/product/auth-session-routing.md), the cookie identifies a
*requested* organization context only; every read re-validates it
against the caller's own live, active Memberships, and it is never
treated as authorization by itself.
