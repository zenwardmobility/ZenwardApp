--------------------------------------------------------------------
1. S5A ORDERING DISCOVERED
--------------------------------------------------------------------
P1-E3-S5A's `reassign_trip` checked the idempotent driver/vehicle match
BEFORE verifying `p_expected_assignment_id` against the active
assignment. Concretely: if the active assignment changed from X to Y
between when a Dispatcher loaded the Trip and when they submitted, and
the Dispatcher's own requested driver/vehicle happened to equal Y's
(coincidentally, or because two Dispatchers independently reached the
same conclusion), the RPC matched on driver/vehicle FIRST and returned
`changed:false` — a silent, "successful" no-op — without ever checking
whether the Dispatcher's own expectation (X) was actually still
current.

--------------------------------------------------------------------
2. WHY IT VIOLATED THE REQUESTED CONTRACT
--------------------------------------------------------------------
The explicit product rule (both P1-E3-S5A's own originating work item
and this phase's) is: **a stale expected assignment must NOT be
treated as an idempotent success.** S5A's ordering treated it as
exactly that in one specific case — "stale, but the request happens to
match the current state anyway." The RPC's own hardening comment even
said so ("the current state already happens to equal what THIS caller
wants... there is nothing to overwrite here") — a reasonable-sounding
argument that the originating work item's own explicit language
(§2/§3, "EVEN IF requested driver == current driver AND requested
vehicle == current vehicle") directly overrides: staleness is
staleness, independent of what the stale request happens to ask for.

--------------------------------------------------------------------
3. SQL ORDERING BEFORE
--------------------------------------------------------------------
```
lock active assignment
if no active assignment -> ZW005
if driver+vehicle already match active assignment -> changed:false  [1st]
if expected_assignment_id != active assignment id -> ZW005          [2nd]
... proceed with real reassignment ...
```

--------------------------------------------------------------------
4. SQL ORDERING AFTER
--------------------------------------------------------------------
```
lock active assignment
if no active assignment -> ZW005
if expected_assignment_id != active assignment id -> ZW005          [1st]
if driver+vehicle already match active assignment -> changed:false  [2nd]
... proceed with real reassignment ...
```
Matches the canonical sequence in work item §2 exactly: authorize →
validate Trip/state → lock current active assignment → active
assignment must exist → expected assignment ID must match → THEN
evaluate idempotent driver/vehicle match → validate replacement →
atomically close+create → event/audit unchanged. Implemented by
editing `supabase/migrations/20260901120000_reassignment_concurrency_
hardening.sql` in place (the S5A migration, never deployed or
committed) — a fresh `supabase db reset` produces the corrected
function directly, with no intermediate "wrong then right" migration
step. See decision-register.md ZD-146 for the full reasoning, including
why editing this specific file in place (rather than layering a new
migration on top) is the safe choice here and not a violation of this
project's own "never edit historical migrations" convention (this file
is same-day, same-session, uncommitted churn, not deployed history).

closing the dialog, the board — refreshed — correctly shows Driver 2
(the real current state), not a fabricated distinction from what A
also wanted. This is the exact previously-missing guarantee: the
request "coincidentally" matching reality no longer disguises a stale
decision as a safe no-op. PASS (6/6 sub-assertions, SQL C12c also
PASS).
