2. ACCOUNT MENU — ISSUE AND FIX
--------------------------------------------------------------------
**Root cause, not just a CSS symptom.** `getDisplayName()`
(`src/lib/auth/profile.ts`) falls back to the raw email address
whenever a signed-in user has no `user_profiles.display_name` row —
correct, deliberate, already-tested behavior in general (the QA
fixture organizations genuinely rely on this fallback and remain
unaffected — see §9). The problem was specific to Harmony's own
Operations-facing staff: `owner@harmonytransport.test` and
`dispatch@harmonytransport.test` had no `user_profiles` row, so their
full email address rendered in the sidebar's identity slot — a slot
sized and styled for a short human name, not an email address. That
mismatch, not a missing CSS rule, is what actually produced the
"awkward truncation" the S8C audit flagged.

**Two-part fix, both applied:**
1. **Data (root cause):** `supabase/seed.sql` now seeds real
   `user_profiles.display_name` rows for all 5 Harmony auth users —
   "Renata Castillo" (organization_admin), "Sam Delgado" (dispatcher),
   and the 3 drivers' own names (for completeness/consistency, though
   Driver UI never reads this table — it uses `drivers.display_name`
   directly).
2. **Layout (defense in depth):** `OperationsSidebar.tsx`'s bottom
   identity block gained `min-w-0 flex-1` on the text container (a
   flex child with no explicit width never actually shrinks without
   it, so the existing lack of a width constraint is why a long value
   previously overflowed rather than ellipsizing) plus `truncate` and
   a `title` attribute on both the name and role lines.
   `AccountMenu.tsx`'s popup header got the same `truncate`/`title`
   treatment on both its organization-name and role lines, and its
   container gained `min-w-0`. The popup itself was NOT widened
   (still `w-56`) — "no huge popup" per the work item.

**Verified live** (fresh reset, signed in as
`dispatch@harmonytransport.test`, 1440×900 viewport): the sidebar
identity block reads "Sam Delgado / Dispatcher" cleanly, no clipping,
no overflow. The account-menu popup opens at 224px wide, showing
"Harmony Medical Transport / Dispatcher" fully readable with no
truncation needed at this org name's actual length; the `title`
attribute stands ready for a longer org name in the future.
Keyboard/accessibility behavior (Escape, click-outside, `aria-
haspopup`/`aria-expanded`/`role="menu"`) is unchanged — no
interaction logic was touched, only the identity-text markup/classes.
No additional personal data is exposed — the same two fields (name,
role) render as before; only their layout resilience changed.

3. "TRIPS TODAY" SEMANTICS — DEFINITIONS AND FINAL LABELS
--------------------------------------------------------------------
Inspected the actual queries directly (not assumed from either
screen's own prior report language):

  Today's Operations `todayCount`  (src/lib/operations/todays-
    operations.ts): `todayTrips.length` — every trip whose
    `scheduled_pickup_at` falls within the organization's local
    "today," in ANY state. Includes trips already completed,
    cancelled, or no-show.

  Dispatch `todayCount`  (src/lib/operations/dispatch-board.ts):
    `trips.length`, where `trips` was ALREADY filtered to
    `NON_TERMINAL_STATES` before this count was computed (line ~205
    of that file) — i.e., only trips still actionable today. This
    scope was already correct and intentional (a dispatch board's
    natural job is "what still needs handling," not "everything that
    happened today") — nothing about the underlying query changed
    this phase.

Both numbers were already right for their own screen's purpose; only
the shared label ("trips today" on both) made them read as
contradictory. **Final labels:**

  Today's Operations:  "trips today"       (unchanged — this screen's
                        own scope genuinely IS the full day)
  Dispatch:             "open trips today"  (renamed — makes the
                        already-correct non-terminal scope explicit)

No operational logic was changed to force the numbers to match — the
work item's own explicit instruction, and correctly so: the two
scopes are genuinely different and both are useful. In-code comments
were added at both `summary: {...}` definitions
